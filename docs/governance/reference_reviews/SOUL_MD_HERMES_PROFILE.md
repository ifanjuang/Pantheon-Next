The reviewed repository presents `SOUL.md` files as reusable personality layers for AI systems that should behave with identity, taste and conviction.

```text
AGENTS.md -> project-specific working rules, architecture and conventions
```

Hermes Agent documentation describes `SOUL.md` as a durable persona file under `HERMES_HOME`, loaded as the primary identity layer, while project rules belong elsewhere.

## Governance problem

Generic execution profiles drift.

A generic agent may:

- over-adapt its tone to user pressure;
- avoid useful pushback;
- hide uncertainty behind smoothness;
- behave inconsistently across long tasks;
- confuse style compliance with governance compliance;
- produce candidates that are harder to review because its stance is unclear.

Pantheon needs Hermes execution profiles that are predictable enough to produce reviewable candidates without becoming governance authorities.

## Pantheon distillation

Pantheon may distill `SOUL.md` as a profile identity pattern for Hermes only.

The useful pattern is:

```text
stable execution posture -> clearer candidate behavior -> easier governance review
```

A Hermes profile may define:

- identity posture;
- communication tone;
- uncertainty behavior;
- pushback behavior;
- capability-gap behavior;
- hard stops;
- evidence discipline;
- escalation reflexes.

This can improve execution quality and candidate legibility.

It does not change authority.

## Forbidden import

Pantheon must not import:

```text

persona as approval mechanism
persona as memory authority
persona as Task Contract substitute
```

A personality file must never decide what is true, approved, canonical, transmissible or memorable.

## Required hierarchy

If a Hermes profile identity layer conflicts with governance doctrine, governance wins.

Authority order:

```text
Pantheon doctrine
Task Contract
Context Pack
External Tools Policy
Approval requirements
Evidence expectations
Hermes profile identity
Runtime-local style preference
```

A profile may shape how execution is performed.

It must not alter what execution is authorized to do.

Pantheon profiles should prefer professional execution posture over theatrical identity.

## Good pattern

Good:

```text
You are a source-review execution profile.
You prioritize provenance, versioning, contradiction detection and source freshness.
When evidence is insufficient, you say so and return a capability gap instead of smoothing the answer.
You produce Evidence Pack material only; you do not approve evidence.
```

Bad:

```text
You are ARGOS, the all-seeing judge of truth.
You decide which sources are valid and store final conclusions for later use.
```

The first stabilizes execution.

The second collapses profile, role, approval and memory.

## Interaction with Pantheon Roles

Pantheon Roles are governance roles.

Hermes profiles are execution profiles.

A Hermes profile may be aligned with a Pantheon Role name only when the boundary remains explicit.

Example:

```text
ARGOS as Pantheon Role -> source governance viewpoint
argos-agent as Hermes profile -> source review candidate producer
SOUL-like identity layer -> stable posture for the argos-agent profile
```

The identity layer does not create role authority.

## Interaction with Task Contracts

A Task Contract may request a Hermes profile with a given posture.

It must not request personality as permission.

Allowed:

```text
Use a source-review Hermes profile to prepare provenance notes.
```

Forbidden:

```text
Use the Argos personality to decide final source truth.
```

## Interaction with Evidence Packs

When profile behavior affects a candidate output, the Evidence Pack may record:

```text
profile used
profile scope
profile limitation
capability gaps reported
uncertainty surfaced
review notes produced
```

The Evidence Pack should not store theatrical persona text unless it is directly relevant to review.

## Interaction with memory

Profile identity is context or runtime configuration.

It is not Canonical Memory.

A recurring profile behavior may inspire a Memory Candidate only if the claim is scoped, evidenced and approved.

No profile may promote memory automatically.

## Interaction with OpenWebUI

OpenWebUI may expose selected profile information for user clarity.

Useful cockpit display:

```text
profile selected
profile purpose
profile scope
profile limits
expected output type
approval boundary
```

OpenWebUI must not present profile selection as approval, truth or memory.

## Failure modes

Common failure modes:

- persona theatre replaces professional discipline;
- role names become agent identities;
- profile confidence becomes evidence confidence;
- stable voice masks weak sources;
- profile-specific preferences override Task Contract scope;
- user pressure rewrites the identity layer mid-task;
- a profile claims authority because it sounds decisive;
- a SOUL-like file becomes a hidden policy override.

## Governance checks

Before using a SOUL-like identity layer for Hermes, check:

```text
Is it execution posture only?
Is the Task Contract still the boundary?
Are approvals untouched?
Is memory promotion forbidden?
Are tool permissions unchanged?
Is uncertainty behavior explicit?
Is capability-gap reporting explicit?
Does it avoid role-authority language?
```

If any answer fails, the profile should be revised or rejected.
