# Pantheon RPG Visual System

Status: conceptual visual asset — not implemented governance doctrine.

This directory defines the visual design, narrative structure and development roadmap for the Pantheon Next RPG poster series.

It is a communication and explanation layer.

It is not a runtime module, not a workflow engine, not an execution surface and not a source of canonical governance by itself.

## Core idea

Pantheon Next is represented as a governed decision RPG.

The user is the player.

The player explores sources, invokes companions, crafts deliverables, avoids traps and saves only what has been validated.

```text
The system prepares.
The human decides.
Validated content remains.
```

The visual metaphor must preserve the central project doctrine:

```text
OpenWebUI exposes.
Hermes Agent executes.
Pantheon Next governs.
```

For public-facing visuals, this doctrine is translated into game-world language:

```text
The interface is the visible cockpit.
The workshops execute craft actions.
The city governs memory, evidence and validation.
```

The poster must not foreground technical terms such as runtime, provider, vector store, backend, queue, scheduler, LangChain, LangGraph, RAG, embedding or API architecture.

## Purpose

The visual system exists to explain Pantheon Next to non-technical users:

- architects;
- doctors;
- lawyers;
- experts;
- public bodies;
- consultants;
- project teams;
- decision-makers.

The goal is not to explain a software stack.

The goal is to make the work experience understandable:

1. choose a quest;
2. bring source material;
3. explore available knowledge;
4. invoke the right companions;
5. use skills and tools;
6. detect risks and traps;
7. receive evidence and a deliverable;
8. validate, modify or relaunch;
9. save only what has been validated.

## Visual doctrine

The visual world must remain a real RPG world, not a decorated diagram.

Required direction:

- vertical isometric pixel art poster;
- 16-bit / 32-bit strategic RPG feel;
- Greek antique city;
- cut-stone architecture;
- terracotta roofs;
- columns, stoas, agoras, temples, propylons;
- ports, roads, bridges, rivers, forests, hills and ruins;
- underground workshops and forge spaces;
- visible player agency;
- readable companions;
- visible source verification;
- visible project memory separation.

Forbidden direction:

- medieval castle;
- fantasy battlements;
- SaaS dashboard;
- flat corporate infographic;
- modern technical architecture chart;
- cyberpunk interface;
- data center imagery;
- autonomous agent control room;
- fake smooth 3D render.

## Reading levels

The poster must support three reading levels.

### Three seconds

The viewer must understand:

- the user is the player;
- the player chooses a quest;
- companions help;
- memory is a city;
- nothing durable is saved without validation.

### Ten seconds

The viewer must understand:

- sources come from outside;
- sources stop at verification docks;
- knowledge remains outside the city until validated;
- companions help produce and review;
- the user validates;
- the final deliverable joins the right memory area.

### One minute

The viewer must understand:

- domains;
- entry and output channels;
- source categories;
- quests and side quests;
- oracles;
- evolving skills;
- tools and armory;
- loot and evidence;
- project districts;
- sessions and discussions;
- traps and cognitive risks;
- memory compartmentalization.

## Canonical spatial composition

The poster is a vertical cutaway of the Pantheon world.

It contains four major strata.

```text
Cieux des Possibles
Monde Extérieur
Cité de la Mémoire
Ateliers Souterrains
```

The flow must remain clear:

```text
player input
→ source collection
→ verification docks
→ quest orientation
→ companion invocation
→ craft and review
→ evidence and deliverable
→ human validation
→ controlled memory update
```

They must not appear as a place that governs the city.

They illuminate choices.

### Maritime sources

External sources are represented by boats.

Boats never enter the city.

They stop at the docks.

Source ships:

- simple web page = small rowboat;
- social networks = corsair ship;
- open data = fishing boat with nets and crates;
- SaaS platform = merchant ship;
- public API = service ship with cranes and connectors;
- official sources = state galley with seal and banner;
- dark web = black ship far outside the map.

Acceptance criteria:

- boats remain outside the city;
- source categories are visually distinct;
- no channel such as email, WhatsApp or calendar is confused with maritime source routes.

### Verification docks

The verification docks are the controlled threshold between external sources and governed work.

Visual elements:

- antique harbor;
- stone docks;
- guards;
- scribes;
- registers;
- inspected scrolls;
- open crates;
- stamps;
- seals;
- controlled gates.

Source states:

```text

read = blue seal

verified = green seal
validated = gold seal
archived = violet seal
```

Acceptance criteria:

- the viewer understands that source provenance is inspected;
- external information cannot become memory by accident;
- verification is visible before any memory update.

## Traps and enemies

Traps represent real epistemic and operational risks.

They should be playful but meaningful.

```text
context fog = unclear request or incomplete file
sirens of easy sources = attractive but unverified answers
duplicate goblins = repeated documents and conflicting versions
proof mimics = fake evidence or doubtful citations
assumption marsh = undeclared assumptions
old-version ghosts = obsolete decisions
contradiction troll = incoherent sources
social media pirates = noise and rumor
overload dragon = too much information
administrative labyrinth = complex forms and rules
unsealed gate = non-validated information
broken bridge = missing link between source and conclusion
```

Acceptance criteria:

- traps explain why governance matters;
- enemies remain tied to real risks;
- the visual does not become fantasy decoration only.

## Current open risks

### Risk: overload

A single poster may become unreadable if every label, god, tool, quest and trap is shown at equal weight.

Mitigation:

- keep the master poster mostly visual;
- use short labels only;
- reserve long explanation for this README;
- split into four boards if needed.

### Risk: metaphor drift

The RPG metaphor could imply that Pantheon is an autonomous runtime.

Mitigation:

- keep the player central;
- show companions as helpers;
- show validation gates;
- show external sources stopping at docks;
- show workshops as craft zones, not control rooms.

### Risk: memory confusion

Viewers may confuse knowledge, source, context and memory.

Mitigation:

- boats = external sources;
- fields = consultable knowledge;
- docks = verification;
- city = governed memory;
- districts = project-scoped memory;
- palace = system memory;
- sealed deliverable = validated output.

### Risk: Greek city confusion

The city could drift toward medieval fantasy.

Mitigation:

- require Greek antique architectural vocabulary;
- forbid castles, crenellations and fantasy battlements;
- use temples, stoas, agoras, propylons, limestone and terracotta.

## Definition of done for the first complete poster

The first complete poster is acceptable when:

- it reads as a game world before it reads as a diagram;
- it is understandable by a non-technical user;
- the player remains the active decision-maker;
- gods assist but do not decide;
- source boats stop at the docks;

- underground workshops craft deliverables without looking like a backend;
- validation is visually explicit;
- only validated content is shown entering durable memory;
- the visual does not introduce runtime, scheduler, provider router or autonomous execution concepts.
